# ADR-0002: The reactive arm is Polaris's observed-τ, unchanged

Status: accepted 2026-08-28, no runs yet. See `surgical/BRIEF_surgical.md` for the
experiment design and `surgical/CODE_AUDIT.md` for the code-readiness audit.

## Context

The supervisor asked for a surgical comparison of speed estimators: GPU spec, CPU
spec, and history-based. The first two exist as the `gpu` and `cpu` arms. The third
did not exist as an arm — but a reactive estimator was already in the codebase, as
the default fall-through predictor `"observed"`, lifted from the Polaris
implementation at `examples/client_selection/polaris/`.

Two questions had to be settled before any code was written.

**1. Which reactive estimator?** Two are defensible:

* *observed-τ (rounds)* — Polaris's: store the staleness in rounds that was measured
  when the client last reported, and reuse it.
* *history-in-seconds* — estimate the client's training time `T_i` in seconds
  (e.g. an EMA of reported training times), then convert to rounds through the same
  live `T_round` the spec arms use.

**2. Does the `+0.1` offset stay?** Polaris stores `staleness + 0.1`
(`polaris_selection_strategy.py:129`); this repo's port stores the raw value with a
comment explaining that inflating every client equally destroys differentiation
(`fedasync_polaris_vi_selection.py:137`).

## Decision

### 1. The reactive arm is Polaris's observed-τ. There is no history-in-seconds arm.

Reasons:

* It is **paper-anchored**. "We compared against Polaris's staleness estimator" is a
  defensible claim; "we compared against an EMA we designed" invites the reviewer to
  ask why that EMA and not another.
* It **already exists and has run** — no new estimator logic, no new failure modes
  (`CODE_AUDIT.md` § 1).
* A history-in-seconds arm would, under this simulator, be an **oracle**: reality is
  a static per-client sleep read once from a CSV with `noise_sigma = 0`, so one
  observation recovers `T_i` exactly and the arm would measure nothing but cold-start
  cost. It was considered as an upper-bound control and rejected as not worth its
  run time.

### 2. No `+0.1`. Keep this repository's implementation.

The offset is added identically to every client, so it barely moves the ranking that
`V_i` produces, and the existing behaviour has already been exercised. The
difference is recorded here and must be stated wherever this arm is described as
"Polaris", together with the larger departure: we use Polaris's **staleness
estimator**, not its geometric program — that requires cvxopt + mosek and is not
what is being tested.

### 3. The asymmetric `T_round` handling is the treatment, not a defect

The spec arms recompute `T_round` live from the busy pool each round
(`fedasync_polaris_vi_selection.py:213-226`); the observed arm stores τ already in
rounds and never rescales it. This is not an oversight to be harmonised away.

The estimand decomposes as `τ_i(t) = T_i / T_round(t)`, where the denominator is
endogenous — `HANDOFF.md` § 4.9 models staleness as `(C/M)·(T_i / T_mean_selected)`,
and `T_mean_selected` is the mean duration of the clients that arm chose. So the
three arms fail differently: `cpu` has a wrong `T_i`, `observed` has a stale
`T_round`, `gpu` has neither. Measuring that difference is the experiment.

An earlier draft proposed injecting per-round noise or a mid-run tier reassignment
to give the reactive arm something to get wrong. That is now rejected as
unnecessary: the non-stationarity is already present, generated by the selector
itself, and is a more defensible source than an injected constant. **Reality stays
static** (`noise_sigma = 0`, sleep read once from the CSV).

## Consequences

* One new template and one new `ARMS` entry; no new predictor code
  (`CODE_AUDIT.md` § 2).
* Between the `gpu` and `observed` arms the rendered configs differ in exactly three
  keys — `base_path`, `port`, `staleness_predictor` — since the observed arm carries
  the same GPU tier spec for its log labels. Worth asserting in the generator.
* `staleness_predictor` must become strict. Its silent fallback now maps an
  unrecognised value onto a *real arm of the same sweep*, so a typo would produce an
  undetectable duplicate (`CODE_AUDIT.md` § 3).
* The primary metric becomes MAE of τ̂ per tier, not time-to-accuracy. It measures
  the thing this ADR is about and does not carry the ±10 % evaluation-noise floor.
