THE SOURCE THAT SEEDING CANNOT REMOVE

PLATO builds each report's finish time as

    training_time + processing_time + comm_time + start_time
                                     (plato/servers/base.py:1025-1030)

and that finish time becomes the simulated clock. Of those four terms:

    training_time     the client's fixed sleep -- deterministic
    comm_time         0 under comm_simulation = true
    start_time        derived from the clock itself
    processing_time   time.perf_counter() measured ON THE HOST
                      (plato/clients/strategies/defaults.py:252)

`processing_time` is real elapsed time on a shared machine. It is added
to every report, so it enters the clock on every round, and no seeding
can make it repeat. `sim_time_s` therefore CANNOT be bit-identical
between two runs; this is a property of PLATO's clock, not of this
configuration, and it applies to every cell this project has ever run.

4. WHICH WORKER PROCESS SERVED WHICH CLIENT
------------------------------------------------------------------------
PLATO runs a pool of max_concurrency worker processes and gives each
round's selected client to whichever worker is free
(plato/servers/base.py:662-682). The first clients each worker served:

process    run A                        run B                       
1          [18]                         [18]                        
2          [14]                         [15]                           <-- differs
3          [20, 4, 13, 8, 19, 16]       [20, 4, 13, 8, 19, 16]      
4          [15]                         [14]                           <-- differs

THE WORKER ASSIGNMENT DIFFERS, and it differs BEFORE the dispatch
sequence does. That ordering comes from the order the four client
processes happened to connect over socket.io, which is a real-time
race at startup and is not seeded by anything.


Why that is enough to diverge the whole run: the torch RNG lives in
the WORKER PROCESS, not in the logical client. A client trained by
worker 2 in one run and worker 4 in the other draws a different
augmentation sequence (RandomHorizontalFlip + RandomCrop), so it
computes different gradients. From there:

    different gradients -> different G_i
                        -> different V_i = G_i / sqrt(1 + tau_hat)
                        -> a different client is selected
                        -> a different clock

which is exactly the order the sections above observed it in:
train_loss diverges within a handful of rounds, the dispatch
sequence some rounds later.

NOT WORKED AROUND. Recording it is the point. What would fix it is
re-seeding torch at the start of each local training run from
(base_seed, client_id, round) instead of once per process, which
would make a client's augmentation a property of the CLIENT rather
than of the worker that happened to serve it. That is a change to
what the runs do -- each client's augmentation becomes a
deterministic function of the round -- so it is reported here as a
decision rather than applied.
