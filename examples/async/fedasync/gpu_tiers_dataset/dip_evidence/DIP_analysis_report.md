# Accuracy dips: where do they come from?

Log-only analysis. Spec: `prompts/DIP_analysis.md`. Generated by `sumo_open_loop/dip_analysis.py`; every dip interval is listed in `dip_intervals.csv`. Run folders were only read.

## Step 0: what is available

1. **Mixing and staleness.** Config: `mixing_hyperparameter = 0.5`, `adaptive_mixing = true`, `staleness_weighting_function = polynomial, a = 0.5`. Applied weight **w = 0.5 · (τ + 1)^−0.5** (`plato/servers/strategies/aggregation/fedasync.py:157–186`, `_staleness_function`; per update in arrival order with τ + idx in `examples/async/fedasync/fedasync_aggregation.py:66–90`). The merge is `x ← (1 − w)·x + w·x_client` on **every entry of the model state_dict** (`examples/async/fedasync/fedasync_algorithm.py:16–19`). That includes the BatchNorm running mean / variance buffers. Because `w` is a fixed function of τ, "high w" and "low τ" are the same thing: the largest weight, 0.5, goes to a fresh (τ = 0) update.
2. **Logged per merge.** `w`, τ and the client slot are logged directly on every merge (`FedAsync: step k - client #slot, effective_round, staleness, mixing`), so `w` is **read, not recomputed**. Tier and partition come from the dispatch the merge belongs to (`[Stage7] dispatch … tier … partition`), joined as in `analyze_stage7.parse`; every merge in every run was joined (τ cross-checked). Most frequent w values (first run): 0.0928, 0.1043, 0.1066, 0.1091, 0.1118, 0.1147. Partition label skew comes from Plato's Dirichlet sampler, rebuilt for each run's data seed. It matches the partition fingerprints the clients logged: stage13nf s4126/baseline 20/20, stage13f s4126/baseline 20/20, stage13f s4126/gpu 20/20, stage13f s4126/observed 20/20, stage13f s4126/cpu 20/20, stage13rep s4126/baseline 20/20, stage10f1 s4126/baseline 20/20, stage10f1 s4126/gpu 20/20, stage10f1 s4127/baseline 20/20, stage10f1 s4127/gpu 20/20, stage10f1 s4128/baseline 20/20, stage10f1 s4128/gpu 20/20.
3. **Checkpoints.** No global-model checkpoint survives for these runs: the queue deletes each run's `checkpoints/` when it ends. (`stage13f_s4126_gpu_open/checkpoints/` exists but is empty; it was created by a config-loading test on 2026-10-04.) So the dips can only be studied from the logs.

## Reading

**Which quantity separates dip intervals from the rest: the total weight merged, w_sum.**

**The separator.**
- Dip intervals carry more of the global model's mass handed to client
  updates in the preceding 10 rounds.
- AUC is 0.71 (CIFAR-100) and 0.73 (CIFAR-10), rank-biserial +0.42 / +0.46.
  It holds in every one of the 12 runs (per-run AUC 0.55–0.84).
- The dip rate rises steadily across the w_sum quartiles:
  - CIFAR-100: 1.1% → 2.1% → 4.4% → 7.8%;
  - CIFAR-10: 1.3% → 6.3% → 10.3% → 19.0%.
  That is a 7× to 15× difference between the lightest and heaviest quarter.

**What makes w_sum large.** It is not one merge.
- w depends only on staleness, and the number of merges per interval is
  constant (10). So a high w_sum means more fresh, full-weight (w = 0.5,
  τ = 0) merges in a row: median 5 vs 3 (CIFAR-100) and 4 vs 3 (CIFAR-10).
- The largest single weight (w_max) separates only weakly (AUC 0.56–0.58).
  Most intervals contain at least one w = 0.5 merge (82–87%).
- Using the latest of the tied full-weight merges, the dip evaluation more
  often has one in the evaluated round itself: 44% vs 34% (CIFAR-100) and 56%
  vs 29% (CIFAR-10). The pull is recent.

**What does not separate.**
- Staleness max: AUC ≈ 0.5.
- Tier: the top merge is orin or thor in dip and other intervals alike.
  xavier counts differ by at most one merge.
- Partition skew, in CIFAR-100: AUC 0.46–0.51. Its Dirichlet over 100 labels
  gives every partition a largest class of only about 7–8%.
- Partition skew in CIFAR-10 is a secondary signal. Pooled, the dips follow
  merges from more skewed partitions: largest-class share 0.51 vs 0.43,
  AUC 0.68. But it is not consistent across seeds: entropy AUC is 0.21–0.33
  in four runs and 0.54–0.56 in both seed-4127 runs.

**Arms.**
- Dip frequency is about the same in every arm:
  - CIFAR-10: baseline+F 9.1% vs gpu+F 9.3% mean over three seeds;
  - CIFAR-100: 3.1–4.6% across all six runs, including random selection
    without the filter.
- So **the dips come from the FedAsync training dynamics, not from any
  selector**.

**Strength and caveats.**
- This is a strong association, not proof of cause. No global-model
  checkpoint survives to test a merge directly.
- The mixing also averages the BatchNorm running statistics with the same w.
  The logs cannot separate weights from statistics.
- Report only; no fix is proposed or tested here.
