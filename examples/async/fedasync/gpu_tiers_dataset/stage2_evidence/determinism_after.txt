THE SOURCE THAT SEEDING CANNOT REMOVE

PLATO builds each report's finish time as

    training_time + processing_time + comm_time + start_time
                                     (plato/servers/base.py:1025-1030)

and that finish time becomes the simulated clock. Of those four terms:

    training_time     the client's fixed sleep -- deterministic
    comm_time         0 under comm_simulation = true
    start_time        derived from the clock itself
    processing_time   time.perf_counter() measured ON THE HOST
                      (plato/clients/strategies/defaults.py:252)

`processing_time` is real elapsed time on a shared machine. It is added
to every report, so it enters the clock on every round, and no seeding
can make it repeat. `sim_time_s` therefore CANNOT be bit-identical
between two runs; this is a property of PLATO's clock, not of this
configuration, and it applies to every cell this project has ever run.

4. WHICH WORKER PROCESS SERVED WHICH CLIENT
------------------------------------------------------------------------
PLATO runs a pool of max_concurrency worker processes and gives each
round's selected client to whichever worker is free
(plato/servers/base.py:662-682). The first clients each worker served:

process    run A                        run B                       
1          [15]                         [14]                           <-- differs
2          [18]                         [20, 4, 13, 8, 19, 16]         <-- differs
3          [20, 4, 13, 8, 19, 16]       [15]                           <-- differs
4          [14]                         [18]                           <-- differs

The worker assignment still differs -- Change B does not stop the
socket.io connection race, it makes the race HARMLESS. With
ClientSeededTrainer active, torch is re-seeded from
(base_seed, client_id, round) at the top of every local training
run, so a client trained by worker 2 in one run and worker 4 in the
other draws the SAME augmentation sequence.

That it no longer propagates is visible in the sections above:
training stayed bit-identical for far longer than before, and the
divergence, when it came, did not start at the worker assignment.
Section 6 locates what it did start at.

the 3 clients that swapped (#7, #10, #20) finish within 0.592 s of each other

The per-report processing_time measured on this box is ~0.065 s, and
it accumulates PER SLOT, so two slots can differ by several tenths of
a second by this point in a run (stage2_evidence/clock_reconstruction.md
C1). A gap of that size between two clients' simulated finishes is
therefore inside the noise the host adds, and which of them the server
merges first is decided by the machine rather than by the experiment.
