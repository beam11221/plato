## What this cell is

Stages 3-6 showed the scoring claim is a null **in a closed pool**, and why:
any reactive estimator catches up once it has ~30-70 observations of a client
(k\*). Open population is the regime where that catch-up cannot happen —
10,523 vehicles each cross the RSU **once** and never return, so the server
sees each one ~1.7 times (measured κ, see below).

8 runs: `{baseline, gpu, cpu, observed} × p_recur ∈ {0, 1}`. `p_recur = 1` is
the control — same trace, same arrivals, same windows, **only** the identity
policy differs. Stage 0 filter stays **OFF** (this cell tests scoring, and the
filter is already known to dominate the selector when on).

## Traps already found — these are silent when wrong

1. **A slot can be recycled between dispatch and report.** `_dispatch_vehicle`
   freezes the occupant at dispatch; the sleep rewrite and the coverage verdict
   must both use *that* vehicle, never the current occupant. Getting it wrong
   corrupts the waste numbers with no error.
2. **`hash()` is not stable across processes** (PYTHONHASHSEED). Everything
   keyed on `veh_id` goes through blake2b. The project already hit this once —
   see `gpu_tiers_dataset/client_seeded_trainer.py`'s docstring.
3. **`training_time` must be rewritten BEFORE `super().process_client_info()`** —
   `plato/servers/base.py:1026` is where it becomes the finish time that drives
   the entire simulated timeline.
4. **Slots are held for coverage residency, never for selection.** If that ever
   drifts, occupancy stops being trace-determined and each arm faces a
   different population. The digest above is the check.
5. **Never launch 8 runs at once.** Stage 6 did, hit CUDA OOM on a 20 GB GPU,
   and four runs hung silently for 17 hours with no error and no exit code.
   **Two waves of 4.**
6. **End-of-run occupancy digests differ between arms, and that is normal.**
   Each arm consumes a different amount of the trace in 4,000 rounds, so its
   digest is a shorter or longer prefix of the same stream. Wave 1 measured
   `baseline_open` stopping at t=7,262 s, `gpu_open` 7,463 s, `observed_open`
   6,807 s. Compare `digest_at(csv, 20, T)` at a common T instead. Reading the
   raw digests as a stop-condition trip is a false alarm.
7. **The clock deadlock.** `_advance_clock_to_occupancy` must test
   `_selectable_slots()` (occupied MINUS training MINUS reported-not-merged),
   never `occupied_slots()`. A slot held by a withheld client is not
   dispatchable, so the old guard refused to idle while the selector got an
   empty pool: nothing dispatched, no report, clock frozen. `cpu_open` froze
   at round 2,766 / t=5,239.5 s for 14 hours this way on 2026-09-23. It is the
   same bug `sumo_server._advance_clock_to_coverage` documents for the closed
   cell (cpu arm, round 719, 2026-09-06) — the structure was ported, the
   lesson was not. Regression test: `TestSelectableSlotsGuard`.
8. **Storage is 200 GB.** Run the checkpoint cleaner per run (`run_stage6.sh`
   has the pattern). Finished+analysed runs' `checkpoints/` can be deleted —
   `results/*.csv` and `server_*.log` are what the analysers read.

9. **The proactive predictors are keyed on the SLOT, not the vehicle.**
   `gpu_tops_predict_seconds(cid, …)` → `tier_for(cid)` → the closed-loop
   `clients_n20r400.csv` (1–10 xavier, 11–17 orin, 18–20 thor). In Stages 3–6
   `cid` is a vehicle, so this is correct. In Stage 7 `cid` is a slot, and
   the tier label matches the occupant 37% of the time (chance). This affects
   both `gpu` and `cpu`, and is silent because the physics (`_dispatch_tier`,
   `sumo_open_server.py:295`) is correct. Separately, the dispatch line's
   `tau_hat=` is the observed-τ array, not what a proactive arm used. Full
   write-up: `gpu_tiers_dataset/stage7_evidence/STAGE7_gpu_arm_audit.md`.
   **Status 2026-09-23: `gpu_*` and `cpu_*` must be re-run once fixed;
   `baseline_*` and `observed_*` stand. `p_recur = 1` semantics (no vehicle
   ever returns) is an open decision for the user.**
